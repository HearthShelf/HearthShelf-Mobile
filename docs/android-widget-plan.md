# Android home-screen widget - implementation notes

> **Built 2026-09-10** (commit cddac39). Steps 1 and 2 below shipped; the Step 3
> items are still deferred and are the honest backlog. Kept as the record of what
> the constraints actually were, since most of them are not obvious from the code.

Source: user feedback HS-MOBILEAPP-36 (Pixel 10 Pro XL, Android 17, app 0.9.0).

> "Add an android widget that allows you to resume the current book. It should be
> custom sized, have an image of the book on the left with the title and a play
> button that switches to a pause and skip 15/30 sec buttons. Maybe add a 2nd
> widget that also shows the next book in your q or make it so if its more than 3
> tall it adds that section? It should be reminiscent of the hero card on the home
> page."

Two independent reviews (maximal-intent and skeptical-scope) agreed on the
sequencing below. This document records what was verified in the repo, so the
work does not have to rediscover it.

## Verified constraints

**All widget code must be native Kotlin in a config plugin.** An App Widget runs
in the launcher's process through `RemoteViews`. There is no JS runtime, no
React, no bridge. `android/` is gitignored and regenerated by `expo prebuild`,
so the plugin is the only durable home - exactly as `plugins/hearthshelf-auto/`
already does for Android Auto.

**The plugin scaffolding is a solved problem.** `plugins/hearthshelf-auto/index.js`
already copies Kotlin and `res/` into the generated project, patches the
manifest, injects Gradle deps, and registers an RN package. It also writes
`res/xml/automotive_app_desc.xml`, which is the same shape as the
`appwidget-provider` XML a widget needs. Copy those patterns, including their
idempotency guards.

**`minSdkVersion` is 26** (`app.config.js:348`). Size-bucket `setViewMapping`
and `targetCellWidth`/`targetCellHeight` are API 31+, so responsive sizing needs
an `onAppWidgetOptionsChanged` fallback path, not just the modern API.

**A native-readable state channel already exists**, but it must not be reused
as-is. `HearthShelfAutoModule.kt` owns a `SharedPreferences` file
(`hearthshelf_auto`) that JS writes and the native services read - this is the
right mechanism. The existing `offlineLibrary` key is the wrong payload:

- it contains **only completed downloads** (`carOffline.ts:58` skips anything
  whose status is not `done`), so a streaming-only listener has an empty
  snapshot; and
- it is **gated on car mode** and cleared on the same edge
  (`carOffline.ts:92-95`, plus native `clearSession`), so a user with car mode
  off would get a permanently blank widget.

**There is no native-readable "current book" today.** The home hero derives from
`getItemsInProgress()`, a network call (`app/(tabs)/index.tsx:194`), and the car
service does the same thing over HTTP. A widget cannot do a network round trip on
every update.

**Artwork is already on disk.** `downloads.ts` saves `cover.jpg` per book and
persists `coverUri`, which removes the largest `RemoteViews` risk (it cannot load
network URLs). Stale absolute paths are already rebased for the container-move
case, so the widget must tolerate a missing file rather than assume one.

**The queue is deliberately not persisted locally** (`src/player/queue.ts:2-5`,
"persist server-side... no AsyncStorage here"), so the "up next" section has no
local data source and needs its own channel before it can exist.

**Playback control splits into a cheap case and an expensive one.**
`HearthShelfPlayerService` is a real `MediaSessionService`, so play/pause/skip
against an **already-loaded** book is a `MediaController` call, and skip amounts
come free from the prefs the service already reads. But `load()` is only ever
called from JS - resolving a stream needs an authenticated
`POST /api/items/:id/play`. That resolver exists natively only inside
`HearthShelfAutoService`. Cold-start playback with the app dead is therefore the
expensive part of the word "resume".

## Step 1 - the `nowPlaying` prefs channel (prerequisite)

A new prefs key written by JS on every play/pause/track change: itemId, title,
author, coverUri or null, position, duration, isPlaying, and the resolved
chapter subtitle.

It must be **independent of `offlineLibrary`**: not gated on car mode, not
cleared by `clearSession`, and populated for streaming books too. This single
piece of plumbing unblocks everything below, and nothing else can be built
first.

## Step 2 - one resizable widget (the shippable first version)

- Cover on the left from the on-disk `cover.jpg`, with a typeset placeholder
  fallback (mirror `TypesetCover.tsx`). Decode bounded with `inSampleSize`; a
  full-resolution cover exceeds the ~1.5 MB `RemoteViews` transaction limit and
  renders nothing, silently.
- Title, author, and a thin progress bar.
- Play/pause plus skip-back/skip-forward, driven through the **existing
  MediaSession** - never directly at an ExoPlayer.
- Skip labels read `skipBackSec`/`skipForwardSec` from prefs. The request says
  "15/30", but those are user settings with custom variants, so the numerals
  must follow the setting. Reuse the generated `ic_hs_rewind_*`/`ic_hs_forward_*`
  drawables from `plugins/hearthshelf-auto/android/res/gen-skip-icons.js`, with
  the runtime numeral-drawing path for custom values.
- Live play/pause icon sync pushed from the service's existing
  `onIsPlayingChanged` listener, plus a throttled progress push while playing
  (~10-30s, immediate on play/pause/seek). `updatePeriodMillis` has a 30-minute
  floor and cannot do this.
- Tap elsewhere deep-links to `/player` via the `hearthshelf` scheme.
- **Cold start, first cut: launch the app to the player with an autoplay
  intent** rather than resolving a stream natively. Honest, always works, and
  defers the expensive resolver. Measure whether "it opened the app" is actually
  a complaint before paying for the alternative.
- Distinct empty states - never a blank card, which is the failure `StartHere`
  exists to prevent: nothing ever started; something in progress but not loaded;
  signed out or no server.

### Styling

Evokes the hero card; it cannot be a port. `RemoteViews` has no flexbox,
gradients, shadows, or percentage widths - the scrim must be a layer-list or
baked into the bitmap, and the progress fill becomes a tinted `ProgressBar`.

Use the hero's **content-anchored** constants (`HERO_TEXT`, `HERO_TEXT_DIM`,
`HERO_EYEBROW`, `HERO_TRACK` in `app/(tabs)/index.tsx`) rather than theme
tokens. The art is always dark-scrimmed regardless of theme, so this palette is
theme-independent by construction and sidesteps the light-mode contrast class of
bug entirely.

Do **not** introduce Glance for v1. The project has no Compose at all, so it
would add a compiler plugin and new Kotlin constraints against AGP 9 / JDK 21
for a fidelity gain that should be judged on a real device first.

2. ~~**The up-next section**~~ - SHIPPED. It got its own `widgetQueue` prefs

3. **A second dedicated queue widget**, only once the provider and snapshot are

4. Per-instance configuration (pin a book vs. always-current).

## Standing hazards

**A widget is a third playback control surface.** The two-player split between
the phone `MediaSessionService` and the car `MediaLibraryService` has already
produced several "which player owns playback" bugs. Every widget action must go
through the same MediaSession the notification uses, and must respect the
car-ownership guard - `HearthShelfAutoModule.load` already bails when the car
player is live.

**Widget action to service start is the fragile path.** Android 12+ restricts
foreground-service starts from the background. A play tap with the service dead
must connect via `MediaBrowser`/`MediaController` (exempt for media) rather than
`startForegroundService`, or it throws on exactly the cold-start case the widget
exists for.

**Device-only verification.** Widget behaviour cannot be checked in this
environment; it needs a real Android build (see `TESTING.md`, JDK 21).

Nothing in `packages/core` changes, so no submodule pointer bump is required.
