HearthShelf Mobile

The four screens behind the More menu

QuestGiver, History, Collections and Playlists exist on web but not on mobile. These are the proposed mobile treatments. Tokens come from src/ui/theme.ts; every screen is drawn at real proportions inside a phone frame.

Collections
Small

Standard ABS endpoints. Mobile already reads them for the add-to-list sheet. New: a cover-stack tile.

Playlists
Small

Same shape as Collections, ordered rows instead of a grid. Shares the detail scaffolding.

History
Small

Endpoint and all formatting already exist. Needs paging added to one function, plus one screen.

QuestGiver
Large

Engine is 100% in core already. The work is a 6-step wizard - roughly the other three combined.

A 2-column grid of cover stacks. The tile is the only genuinely new component - four covers plus a +N badge. Tapping opens a detail grid that reuses BookTile.

What the investigation turned up

Three of these are small. One is not.
Collections, Playlists and History are all standard Audiobookshelf reads against endpoints mobile already talks to, with formatting helpers already in core. QuestGiver is roughly the other three combined - an 800-line wizard on web, five bespoke components, plus a new API client. Its recommendation engine, though, is 100% in @hearthshelf/core already and needs no porting.
QuestGiver works with no AI backend
qgHeuristic() in core is a complete deterministic recommender, and every AI path falls back to it on any failure - unconfigured provider, rate limit, network error. Mobile can ship the whole flow before any AI is configured. The only thing the AI adds is "buy/request" picks for books outside the library.
Two web behaviours I would not port
Playlist detail draws a drag handle that reorders nothing - there is no implementation in either web app. And both "New collection" buttons are stubs (one fires a "coming soon" toast, the other has no handler at all). Mobile already has real creation inside AddToListSheet, so the browse screens can just link to it.
A latent bug worth fixing in passing
Mobile's getLibraryCollections / getLibraryPlaylists omit ?limit=0, so they silently truncate at the ABS default page size. It doesn't show today because the add-to-list sheet only needs names, but a browse screen would drop collections with no error. The hosted web app already passes limit=0.
One thing mobile can do that web can't
deleteListeningSession and updateListeningSession already exist in src/api/abs.ts and no web screen uses them. Swipe-to-delete on a History row is close to free, and it fixes the real case the code comments describe: falling asleep and banking six hours you didn't listen to.
Decisions I need from you
1. The two web apps disagree on "Look beyond my library" - self-hosted runs the external search whenever it's on, hosted also requires the request backend, which makes its own help text misleading. Pick one.
2. Collections detail has edit/delete on self-hosted but is read-only on hosted. ABS supports writes in both cases, so this looks like a product choice - does mobile get them?
3. Build order. My suggestion: Collections, Playlists and History first (they unlock three of the four dead menu rows for a fraction of the effort), then QuestGiver on its own.
